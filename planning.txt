- Spec Driven Development overview
Constitution / project rules
Defines the team’s standards and guardrails.
Example: coding style, testing expectations, architecture constraints, 
how PRs are reviewed.
This is the “non-negotiable rules” layer.

Spec creation
Turns vague requests into clear requirements.
Helps reduce ambiguity before implementation starts.
Good for product features, bug fixes, and API changes.

Planning
Breaks a large feature into concrete tasks.
Makes work traceable and easier to estimate.
Helps avoid jumping straight into coding.

Execution / implementation workflow
Executes against the plan in controlled steps.
Encourages small validated changes instead of big risky rewrites.
Often pairs well with test-first development.

Traceability
Links requirements → plan → code → tests.
Very useful when you want to know why something was built and whether it is fully covered.

Quality gates
Confirms a feature is complete before merging.
Example checks: tests pass, requirements mapped, no missing edge cases.

Change control
Keeps requirements from drifting as implementation moves forward.
Helpful in multi-step or longer-lived projects.

Team alignment
Makes it easier for multiple people to work from the same source of truth.
Reduces “I thought this meant something else” problems.


- spec-driven workflow:

Constitution : Rules for how the project should behave and evolve.
Spec-first feature definition : Requirements, acceptance criteria, edge cases.
Task decomposition : A feature is turned into milestones and discrete work items.
Test-first validation :  Write a failing test, then implement against it.
Execution loop : Implement small steps and re-validate.
Review / signoff : Final checks that the feature meets the spec.
Requirement traceability : Each task can be linked back to a requirement.

-- commands
Establish project principles:
/speckit-constitution Create principles for this Python project covering code quality, testing, API design, and simplicity

Create your first feature spec:
/speckit-specify Build a book management API where users can create, list, update, and delete books

Turn the spec into a technical plan:
/speckit-plan Use the existing Python app structure in app/, keep dependencies minimal, and add tests for each endpoint

Break the plan into tasks:
/speckit-tasks

Execute the tasks:
/speckit-implement
